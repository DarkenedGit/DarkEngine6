### What replaced `SceneObjectType`
* Each object is an `Archetype` ([ContentDb.h L79-L93](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/content/ContentDb.h#L79-L93)) with a list of components, a list of named behaviors, and `EditorMeta` (label, category, icon, hotkey, modes, default scale and colour). A registry maps 19 component names and their behaviors to C++ readers ([ContentBuiltin.cpp L855-L881](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/content/ContentBuiltin.cpp#L855-L881)).
* Mods load from `content/` plus `mods/` with `depends`/`loadAfter`, and there is a hot-reload poll. Legacy names resolve through `legacy_aliases.json` plus a C++ seed table.
* The Editor's create menu, palette, icons and hotkeys now come from `EditorMeta`.
* Phase 1 of the plan is done: unknown archetypes are kept as `placeholder` with `rawJson` and written back unchanged. The save archetype length limit is gone.
* `SceneObjectType` survives only in docs.

### What remains of `SceneObjectData`
It is still a ~110-field struct ([SceneTypes.h L50-L170](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/Scene/SceneTypes.h#L50-L170)). It holds every particle field, every light field, every cloud field, stream, spawner, movie, patrol/squad, pickup, dialogue and circuit, plus the new `archetype`/`overridesJson`/`rawJson`/`placeholder`/`dataDriven` fields. Each typed block is now converted to `overrides` JSON in two different places (§2.1). It is still used in 25 non-test files. The heaviest users are `SandboxBoot.cpp` (27), `SceneObjectSpawn` (20), `EditorSpawn` (9), `EditorObject.h` (7) and `Building.cpp` (7).

### Leftover "type" logic: the enum became string compares
The `switch` statements are gone, but about 40 places now compare archetype names, which is the same problem in string form. A mod archetype `mymod:direwolf` that reuses wolf behaviors will **not** get wolf treatment at these sites. A mod archetype that happens to be named `mymod:cube` **will** be treated as a cube, because most compares strip the namespace.

### Bugs from the migration

**Confirmed**
1. **Archetype `Health.max` does nothing for hunters and wolves.** `attachKind` calls `AiSystem::attachHunter` first ([ContentBuiltin.cpp L313-L321](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/content/ContentBuiltin.cpp#L309-L325)). That emplaces `HealthComponent` from `entityCombatFor("hunter").healthMax` ([AiSystem.cpp L242-L250](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/AI/AiSystem.cpp#L242-L250)), which is 48 from `hunter.entity.combat.json`. `ensureHumanoidBody` then skips because health already exists. So the 100 in `hunter.archetype.json` and the 60 in `wolf.archetype.json` are dead values, and so is the C++ fallback `kind == Wolf ? 60 : 100`. Wolves also take hunter regen, because `attachHunter` always reads `"hunter"`.
2. **Health is defined in three places with three different values.** Player: archetype 200, `player.entity.combat.json` 100, `entityCombatDefault("player")` 100, Editor `attachEditorPlayer` 200 ([EditorPlay.cpp L125](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/Editor/EditorPlay.cpp#L125)), Sandbox replica 200 ([SandboxApp.cpp L1347](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/Sandbox/SandboxApp.cpp#L1347)). 200 wins in play. The 100 is dead data that designers will edit and see no effect.
3. **Placement overrides on "payload" components lose fields when the Editor saves.** On load, `stripPayloadOverrides` erases `Mesh`, `Model`, `LocalLight`, `Movie` and six others from `overridesJson` ([SceneFile.cpp L599-L607](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/Scene/SceneFile.cpp#L599-L607)). Only the fields that `SceneObjectData` models are read back: `Mesh.emissive` ([L1783-L1789](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/Scene/SceneFile.cpp#L1783-L1789)) and `Model.gltf` (L1792-L1798). Take a hand-written or mod placement like `"overrides": {"Model": {"gltf": "x.gltf", "anim": "x.anim.json"}}` or `{"Mesh": {"primitive": "sphere"}}`. After one Editor save it keeps only `gltf` and `emissive`. This is the same class of data loss that phase 1 fixed for unknown objects.
4. **Scenes write full override blocks, not diffs.** The writer emits every light, particle and cloud field on every placement ([SceneFile.cpp L863-L1044](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/Scene/SceneFile.cpp#L863-L1044)). You can see it in `level.json`, where `core:ambient_light` carries `inner`, `outer`, `range` and `sourceRadius`, which an ambient light doesn't use. Changing an archetype default therefore never reaches existing placements. This undoes much of the benefit of archetypes. Write only the fields that differ from the archetype's resolved params.
5. **Sandbox can't respawn archetype-based entities from a save.** See `saveRespawn` above. `core:*` and `mod:*` ids log "sandbox has no respawn", while the Editor path handles them. Any runtime-spawned archetype entity, such as a mod spawner unit, won't come back on load.

**Suspected**
6. `stampProceduralId(..., "sandbox/level/archetype/{e.id()}")` ([SandboxBoot.cpp L1090](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/Sandbox/SandboxBoot.cpp#L1090)) keys the save ID on the ECS entity index. Every other bucket uses its own counter. If spawn order changes, for example after a scene edit or a batching change, old saves would match the wrong entities.
7. `core:crow` has empty `components` and `behaviors` ([crow.archetype.json](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/content/archetypes/crow.archetype.json)), but it shows in the Creatures menu. A crow placed directly probably spawns an empty entity. Crows only work as spawner units.
8. `core:particle_emitter` and the light archetypes get their light through a behavior named `light.searchlight`, which maps to `attachLocalLight` ([ContentBuiltin.cpp L881](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/content/ContentBuiltin.cpp#L881)). It works, but the name will confuse mod authors. Rename it `light.local`.
9. `seedLegacyAliases` in C++ ([ContentDb.cpp L101-L136](https://github.com/DarkenedGit/DarkEngine6/blob/a08ee9132e4d84ad15cf6f79d6e52a424f1d0146/content/ContentDb.cpp#L101-L136)) repeats `legacy_aliases.json`, and the two lists differ. The C++ table has every bare name, the JSON has only 11 aliases. If the JSON is meant to be authoritative, a mod can't remove an alias.

## 4. What should stay in code

Don't over-correct. These are engine invariants or hot paths where data would only add lookups and failure modes.

* **Component and behavior *implementations*.** Data picks and parameterises them, and C++ defines them. That's the line the registry already draws. It's right.
* **Per-frame lookups.** Resolve names to `ContentId` and pointers at load or spawn: combat profile pointer, status row index, audio cue `AssetID`. No `findArchetype(string)` or `entityCombatFor("player")` per hit or per frame. The current static cache is fast but blocks hot reload. Keep it fast by invalidating on reload, not by doing string lookups.
* **GPU layouts and limits:** `FoliageRecord` 32 B, `kMaxBones = 64`, `MeshInstanceGpu` 144 B, root signature slots, SRV heap size, foliage draw caps (65,536 instances, 4 kinds × 8 parts), 2,048 physics bodies. Share them between HLSL and C++ through headers (D8) rather than JSON.
* **Network wire format and protocol constants** (`Protocol.h`, `NetTypes.h` sizes). The archetype *table* is negotiated by content hash, which is good. The packet layout stays in code.
* **Save format versioning and migration code.**
* **Numerical safety constants:** clamps, epsilons, NaN guards, `kHardCcMaxSeconds`, the CC DR window (game rules that should be the same in every mod), and `kMaxFoliageSidecarBytes`/`kMaxJsonBytes` (security limits on mod files).
* **Mechanic enums:** `ItemType`, `EquipSlot`, `DamageType`, stack rules and status *mechanics*. Data selects them by name. New mechanics are a C++ feature.
* **Editor ImGui layout code.** Theme colours and metrics go through `UiPalette`/`ImGuiTheme`, but not into JSON.
